The yardstick is the same two cells as the morning comparison. Each cell is a discarded 2-second warmup and three 5-second runs. The median is the middle req/s. p50 and p99 on that row are from that same run. Loadgen is pinned `taskset -c 4-7`. One worker uses `taskset -c 0`. Four workers use `taskset -c 0-3`.

## What the profile showed

Keep-alive was not accept-bound, not Nagle, and not a missing `SO_REUSEPORT`. `TCP_NODELAY` was already set. Four workers already bind with `SO_REUSEPORT`. The response is one `write` of the rendered buffer. `time` and `clock_gettime` go through the vDSO: the ptrace trace has no `time` or `clock_gettime` entries. epoll is level-triggered and already batches. `epoll_wait` was 0.031 per completed request, which is one wait per 32 requests, the size of the event array in `serve_one`.

The cost was userspace, and most of it was the generated scanner. `scan` of the 65-byte GET was 3.6 µs, and one hello step called it several times (`classify`, `teCode`, `expectCode`, `sawCL`, `bodyView`, `framedEnd`, and `crlfEnd` from `headerEnd`). A direct call inside `c/generated/conn.c` is not intercepted by `--wrap`. The Makefile renames the definitions to `scan_uncached` and `crlfEnd_uncached`. `c/scan_cache.c` keeps the last buffer by `memcmp` and returns the integer state. A slice larger than the 65536-byte receive window skips the cache.

After that cache, a userspace cycle sample of the 1-worker server (period 50,000, kernel excluded, 4095 samples from the tail of the run) was flat. About 26% of samples were outside the binary. The hottest function inside it was `admitChoice` at 2.8%, then `isMark` 2.3%, `stepAt` 2.3%, `muro__sess_conn_step` 2.2%, `targetView` 2.1%, `pump` 2.1%, `muro__bytes_cat` 1.9%. Nothing left was large enough to double the server.

Ptrace of the cached 1-worker process, keepalive GET c=32, 26,156 requests, 0 errors, slowed by ptrace to 13,065 req/s:

| syscall | per request |
| --- | --- |
| read | 2.001 |
| epoll_ctl | 1.004 |
| write | 1.000 |
| epoll_wait | 0.031 |
| total | 4.051 |

The second `read` is the `EAGAIN` probe. A 65-byte request fits in the 64KB buffer, so the first `read` already drained the socket. Linux reports a later arrival on level-triggered epoll. The `epoll_ctl` is `sync_watch` after every request. On a keep-alive GET the interest stays read-only, and the previous `EPOLL_CTL_ADD` already registered that.

After both cuts, the same trace shape (50,313 requests, 0 errors, ptrace at 25,144 req/s):

| syscall | per request |
| --- | --- |
| read | 1.001 |
| write | 1.000 |
| epoll_wait | 0.031 |
| epoll_ctl | 0.001 |
| total | 2.041 |

`accept4`, `close`, `fcntl`, and `brk` stayed at startup noise.

A throwaway `make c/muro-hello OPT=-O3` did not move the headline cells (1 worker 61,317 vs 61,157 at `-O2`; 4 workers 180,880 vs 181,861). The default stayed `-O2`. That binary was not committed.

## Fixes

Each number is the median of three 5-second runs after a discarded warmup, 0 errors, 0 non-2xx. The 1-worker cell moves several thousand req/s from one sitting to the next under `powersave`. The 4-worker cell stays inside about 2%.

### `ca654f7` Remember the last scan of a request buffer

| cell | before | after |
| --- | --- | --- |
| 1 worker, keepalive, GET, c=32 | 16,564 | 58,105 |
| 4 workers, keepalive, GET, c=128 | 57,028 | 165,004 |

Microbench of the 65-byte GET, nanoseconds per call, `-O2`, one thread: `scan` 3557 to 11, `step(evBytes)` 13141 to 581, the multi-view hello path 25058 to 543. `httpRender` stayed about 175 ns.

### `bf488fc` Stop reading when the socket already returned a short count

| cell | before | after |
| --- | --- | --- |
| 4 workers, keepalive, GET, c=128 | 165,004 | 174,954 |
| 1 worker, keepalive, GET, c=32 | 58,105 | 56,467 |

The 4-worker runs moved as a cluster (previous max 165,053, new min 174,729). The 1-worker median stayed inside the earlier spread (53k, 58k, 60k before this change). Reads per request went from 2.001 to 1.001. A full-buffer read still loops. A later byte is still reported by level-triggered epoll. A peer FIN that arrives with `EPOLLRDHUP` is still `hangup` on that event.

### `d81a322` Skip `epoll_ctl` when the interest did not change

| cell | before | after |
| --- | --- | --- |
| 4 workers, keepalive, GET, c=128 | 174,954 | 181,861 |
| 1 worker, keepalive, GET, c=32 | 56,467 | 61,157 |

`epoll_ctl` per request went from 1.003 to 0.001. The stored watch bits are updated only after a successful ctl, so a matching pair means epoll already has those bits. Unwatch and a real interest change still call `epoll_ctl`. The poll and kqueue paths were left alone. Poll does not syscall per watch, and kqueue was not the measured backend.

The side-by-side matrix later on this same commit measured the 4-worker cell at 177,775. That is the number next to nginx and h2o below. The 181,861 figure is the isolated before/after for this commit.

## Stop

The keep-alive syscall path is one `read`, one `write`, and one `epoll_wait` per 32 requests. Another adapter tweak does not remove those. `-O3` did not move the 4-worker cell. After the scan cache, the userspace profile is a wide scatter of generated admit, session, and view functions, each around 2%, plus libc. Speeding that walk up means changing the book, or skipping work the book still decides (keep versus close, and Date). A cached whole response would do the second thing, so it was not done.

What I would try next, if the remaining 25% versus nginx is still worth a risky change: make the generated session step cheaper on the one-request keep-alive path without taking the keep/close decision away from the book, and stop allocating in `filter_extra` for the static `Content-Type` line. Neither of those looked large enough, on the evidence above, to close the rest of the gap by itself.
