## CPU pin

Logical CPUs 0–7. Hyperthread siblings: cpu0 with cpu4 (core 0), cpu1 with cpu5 (core 1), cpu2 with cpu6 (core 2), cpu3 with cpu7 (core 3).

| case | server | loadgen |
| --- | --- | --- |
| 1 worker / thread / GOMAXPROCS | `taskset -c 0` | `taskset -c 4-7` |
| 4 workers / threads / GOMAXPROCS | `taskset -c 0-3` | `taskset -c 4-7` |

The server set and the loadgen set are different logical CPUs, and they are siblings of the same four physical cores. That sharing is the same for every server. nginx has no `worker_cpu_affinity`. h2o threads are not pinned one-to-one. They float inside the `taskset` mask, which is also how muro-http's forked workers inherit the parent mask.

## Servers

Ports: muro-http 18180, nginx 18181, h2o 18182, Go 18183. All bind `127.0.0.1`. Listen backlog is 4096, which is `SOMAXCONN` and `net.core.somaxconn` on this host.

muro-http, 1 worker, is one process and one socket (`serve_one`, no `SO_REUSEPORT`). 4 workers on Linux fork four processes, and each binds with `SO_REUSEPORT` (`serve_reuseport`). The log line is `muro-hello: workers 4 reuseport`. The handoff path is the non-Linux build and was not used. `TCP_NODELAY` is set in the host. Idle timeout 60000 ms. `max-connections` 1024.

```
taskset -c 0 ./c/muro-hello --bind 127.0.0.1 --port 18180 --max-connections 1024 --idle-ms 60000 --workers 1 --wait epoll
taskset -c 0-3 ./c/muro-hello --bind 127.0.0.1 --port 18180 --max-connections 1024 --idle-ms 60000 --workers 4 --wait epoll
```

nginx uses `bench/nginx/hello.conf.template` with `worker_processes` 1 or 4. `worker_connections` 8192, `worker_rlimit_nofile` 65536, `use epoll`, `access_log off`, `error_log stderr error`, `daemon off`, `sendfile on`, `tcp_nopush off`, `tcp_nodelay on`, `keepalive_timeout 60s`, `keepalive_requests 10000000`, `default_type text/plain`. The listen line is `127.0.0.1:18181 backlog=4096 reuseport` for both worker counts, so the 1-worker nginx process has `SO_REUSEPORT` set on its one socket. The body is `return 200 "hello\n"`, not a file: the static module answers POST with 405. `sendfile` does not apply to `return`. One config covers both modes. Close mode is the client sending `Connection: close`. Keepalive stays on so a keep-alive run does not reconnect after nginx's default of about 1000 requests.

```
taskset -c CPUS /home/rcc/opt/nginx/sbin/nginx -c bench/compare-2026-11-23-raw/nginx-wN.conf -p /tmp/muro-http-bench-nginx-wN
```

h2o-hello, 1 thread, is one socket. 4 threads is one `SO_REUSEPORT` socket per thread. Accepted sockets set `TCP_NODELAY`.

```
taskset -c 0 ./bench/h2o-hello/h2o-hello --port 18182 --threads 1
taskset -c 0-3 ./bench/h2o-hello/h2o-hello --port 18182 --threads 4
```

Go is one process and one listen socket. `GOMAXPROCS` is 1 or 4. `IdleTimeout` is 60 seconds. The handler reads and discards the body, then writes `hello\n` with `Content-Type: text/plain` and `Content-Length: 6`.

```
GOMAXPROCS=N PORT=18183 taskset -c CPUS ./bench/go-hello/go-hello
```

The four listen models are not the same. 1-worker muro-http and 1-thread h2o are one socket without `SO_REUSEPORT`. 1-worker nginx sets `reuseport` on that single socket. 4-worker muro-http, nginx, and h2o each have one accepting socket per worker or thread. Go is always one socket, with `GOMAXPROCS` goroutines. The CPU cap and the pin set match.

- nginx: `Server: nginx/1.30.7`, `Date`, `Content-Type: text/plain`, `Content-Length: 6`, `Connection`
- h2o: `Connection`, `Content-Length: 6`, `Server: h2o/2.3.0-DEV`, `content-type: text/plain` (no `Date`)
- Go: `Content-Length: 6`, `Content-Type: text/plain`, `Date`, `Connection`

## Method

```
taskset -c 4-7 ./bench/loadgen --host 127.0.0.1 --port PORT --concurrency N --duration SEC --mode keepalive|close --method GET|POST
```

One pthread per concurrency slot. Keep-alive is one TCP connection per thread. Close opens a connection per request and aborts it with `SO_LINGER` 0 so the tuple does not sit in `TIME_WAIT`. Latency starts just before the request write and stops when the response headers and body have been read. Connect is outside that window. p50 and p99 are nearest-rank (`ceil(p/100 * N)`) on 1 µs buckets, reported as the bucket index. A sample at or above 200 ms is counted in `overflow` and in the last bucket. `TCP_NODELAY` is set. `rps` is completed responses divided by wall `elapsed_ms`. Threads finish an in-flight request, so `elapsed_ms` can be a little over the duration. The runner treats loadgen exit 0 and exit 1 as a finished run (exit 1 means the tool saw errors). Nothing in this matrix exited 1.

Warmup `--duration 2` is discarded. Three runs use `--duration 5`. The runner then sleeps 2 seconds and checks that the port is closed before the next server. One server at a time.
